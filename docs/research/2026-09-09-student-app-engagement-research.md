# Student-App Engagement Research — Tranmere Tracker / The Solar Campus

**Date:** 2026-09-09
**Scope:** the student-facing side of the app only. The coach/admin wellbeing dashboard is covered by a separate research effort.
**Status:** research only — no code was written and no existing files were modified.

---

## 1. Executive summary

- **The app is not missing features — it is missing reciprocity.** There are 23 student routes and almost all of them are already real, working pages. What is absent is anything the app gives *back* to a student who engages with it. A student checks in, fills a wellbeing survey, logs a meal, logs a session — and receives nothing in return except another prompt. Every single loop is open-ended.
- **There is no social layer at all, despite ~66 peers on the same platform.** No kudos, no peer recognition, no squad feed, no shared moment, no visible team identity. Chat exists (`app/chat/`) but it is plumbing, not culture. This is the single largest gap versus every app that is actually sticky with this age group, and it is the cheapest thing to add because the users, the roster, the push infra and the chat rooms already exist.
- **Notification budget is already spent — and slightly over-spent.** A Year-1 student on a normal Tuesday can receive 6–9 pushes (3 check-in nudges + 3–5 timetable reminders + lunch-ending + calendar events + AI-report nudge). One of those, the "your weekly focus is ready" push in `app/api/cron/refresh-reports/route.ts`, is generated by a **nightly** cron and fires whenever any `high` priority development area exists — so a "weekly" message can realistically land most nights. There are no per-user notification preferences and no quiet hours anywhere in the codebase. **New features must consolidate, not add.**
- **Pushes are fire-and-forget: there is no in-app inbox.** No `notifications` or `announcements` table exists in `supabase/migrations/`; "broadcasts" are just chat rooms (`app/api/admin/broadcast/route.ts`). A student who has notifications off, or who misses a push, has no way to find out what they missed. A single **Activity / Inbox** surface is the highest-leverage structural fix and it also *reduces* push pressure.
- **The AI report talks at the student and cannot be talked back to.** `lib/ai/player-report.ts` produces a rich JSON report nightly, but it is read-only, uses a four-tier `developing | on_track | performing | elite` label (an evaluative frame the sport-psych literature specifically warns against for adolescents), and is completely disconnected from `/goals`, `/idp` and `/targets` — the three places where the student's own intentions live.
- **Two dashboard tiles are dead ends.** `/veo` and `/catapult` are prominent tiles in the dashboard "My Tools" grid but both render "coming soon / not connected yet" (`app/(student)/veo/page.tsx`, `app/(student)/catapult/page.tsx`). Tapping a tile and hitting a wall teaches students the grid isn't worth exploring.
- **Progress is only ever shown as compliance, never as growth.** Attendance is rendered as a red/amber/green percentage against a 90% target; GPS has a "Personal Bests" block in `components/gps/PlayerDashboard.tsx` that is the *only* progress-framed thing in the whole student app. There is no streak, no "you beat your own number", no season-long narrative, no end-of-week recap.
- **Highest-impact, lowest-risk shortlist:** (1) Weekly Recap, (2) Squad Feed with peer/coach shout-outs, (3) Activity Inbox + notification preferences, (4) Personal-Best & progress framing across the app, (5) making the AI report two-way and goal-linked.

### 2.2 Where AI already runs, and who sees it

`lib/ai.ts` exposes a shared Anthropic client with two models: `claude-haiku-4-5` and `claude-sonnet-4-5`.

**Student-visible AI (3 surfaces):**
1. **AI Development Report** — `lib/ai/player-report.ts` (452L) + `app/(student)/ai-report/page.tsx`. Sonnet. Prompt is built from 30d training logs, 14d nutrition logs, last-10 GPS sessions, last-5 match squad entries with coach ratings, and the player's physical profile. Returns structured JSON: `headline`, `overall_rating`, `strengths[]`, `development_areas[]` (each with `priority`, `position_relevance`, `this_week_action`), `training_plan`, `nutrition_plan`, `gps_targets`, `position_insight`, `this_week_priority`. Cached in `ai_player_reports`, regenerated nightly by `app/api/cron/refresh-reports/route.ts` (02:00, 270s time budget, oldest-first).
2. **AI Coach chat bot** — `app/api/ai/chat/route.ts` + `app/chat/AiCoachButton.tsx`. Sonnet, 512 max tokens, last 20 messages of history, one short system prompt. No student data is injected into its context beyond the student's name and role. No safeguarding routing, no logging beyond `chat_messages`, no age-appropriate guardrails in the system prompt.
3. **AI meal-photo analysis** — `app/api/ai/meal-photo/route.ts` + `components/nutrition/MealPhotoUpload.tsx`.

**Staff-only AI (not visible to students):** `student-insights`, `cohort-report`, `learner-review`, `match-report`, `gps-analysis`, `broadcast-draft`, `suggest-assignment`.

Note on prompt caching: `lib/ai/player-report.ts` carries an explicit comment explaining its system prompt is ~120 tokens, below the 1024-token cacheable minimum, so `cache_control` is deliberately not used there. Any new AI feature with a large stable prefix (e.g. a shared coaching-voice system prompt) *would* qualify.

### 2.4 Where the experience is thin

1. **Dead-end tiles.** `/veo` and `/catapult` occupy 2 of 8 prominent dashboard tiles and both render a "not connected yet" amber banner. `docs/FEATURE-STATUS.md` confirms both are credential-blocked (🔑), waiting on VEO and Catapult API keys.
2. **Navigation is inconsistent between mobile and desktop.** Mobile `BottomNav` primary = Home / Chat / Calendar / Profile; "More" sheet = Documents / Timetable / Coursework / Gym / Targets / Wellbeing. Desktop `SideNav` = Home / Documents / Timetable / Coursework / Moodle / Nutrition / GPS / Chat / Training / Matches / AI Report / Profile. **`/performance` appears in neither** — it is reachable only from a link on the `/catapult` page. `/goals`, `/idp`, `/portfolio`, `/learning-hub`, `/myconcern` are reachable on mobile *only* by scrolling the dashboard.
3. **Wellbeing survey is a one-way extraction.** Submit → "Your responses have been saved. See you in two weeks." The student gets zero feedback, no trend of their own scores, no suggestion, no acknowledgement from a human. `components/wellbeing/WellbeingSparkline.tsx` exists but is used on the staff side.
4. **Match experience is self-report-heavy.** Students log their own goals/assists/rating via `MatchLogForm`. Coach rating is surfaced but only inside the invitation card. There is no post-match moment, no team result, no squad reaction.
5. **Goals / IDP / Targets / AI report are four disconnected planning surfaces.** A student can have a self-set goal in `/goals`, a staff-set IDP in `/idp`, review actions in `/targets`, and an AI `this_week_priority` on `/ai-report` — none of which reference each other.
6. **Already fixed — do not re-suggest:** mobile roster row overlap (`2bbd1d9`), print-report chrome (`35e9188`), PWA stale-bundle self-heal (`c7d4942`), bottom-nav cramming → More sheet (`149cb0a`), missing Chat icon (`d6dd73c`), chat pushes not going via FCM (`45b7412`), GPS timeout on check-in (`0625302`, `03b155a`), dashboard "day off" bug (`066c985`).

## 3. External evidence

### Social validation is the strongest retention mechanic, and it is the one this app has zero of

Strava's kudos system recorded **over 14 billion interactions in 2025, up 20% year on year**, and StriveCloud's analysis attributes the platform's defiance of fitness-app churn to a "participation-first" social model where users log 1 hour of activity for every 2 minutes in-app — i.e. the app is a social artefact of the activity, not a replacement for it. Receiving kudos is associated with *increased* subsequent activity frequency, meaning social reinforcement feeds back into the base behaviour. ([StriveCloud — How Strava Drives App Engagement](https://www.strivecloud.io/blog/app-engagement-strava), [Trophy — Strava Gamification Case Study](https://trophy.so/blog/strava-gamification-case-study))

TeamSnap's own product analysis makes the narrower point that keeping team conversation inside the app is what increases session time and stickiness — logistics alone don't hold anyone. ([TeamSnap Blog](https://www.teamsnap.com/blog/general-sports/the-technology-to-solve-youth-sports-big-problem))

### For adolescents specifically, recognition matters more than at other ages

Recognition is "particularly meaningful during adolescence when peer and community perception holds significant importance"; young athletes who feel their contributions are noticed by the adults running the programme are more likely to stay committed through adversity. Critically, the same source argues for **distributed recognition throughout the season rather than deferring all acknowledgement to end-of-year awards** — frequent small reinforcement beats one big ceremony. Team-voted peer awards and "shout-out boards" are called out as the mechanisms that carry the most weight. ([Digital Record Board — Psychology of Athletic Recognition](https://digitalrecordboard.com/blog/psychology-athletic-recognition-student-athlete-performance/), [Awards America — Beyond MVP](https://awards-america.com/blog/beyond-mvp-student-athlete-recognition.html))

Adolescent athlete engagement is positively associated with team cohesion, and coaches act as key mediators of sport participation — their ability to notice shifts in motivation, behaviour or wellbeing enables timely support. ([Adolescent Athlete Engagement and Team Cohesion in Football, PMC12467869](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12467869/))

### Self-Determination Theory gives the design rules, not generic "gamification"

A review of 15 papers on SDT in behaviour-change technologies extracted **50 concrete design suggestions: 11 for autonomy, 22 for competence, 17 for relatedness** — competence support is the largest category and the most under-served here. SDT interventions that support autonomy, reinforce competence and foster relationships produce measurable gains in self-determined motivation, engagement, perceived wellbeing and intention to remain physically active. ([Designing for Sustained Motivation, *Interacting with Computers*](https://academic.oup.com/iwc/advance-article/doi/10.1093/iwc/iwae040/7760010), [Frontiers in Psychology 2025](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2025.1571559/full), [Nature Scientific Reports](https://www.nature.com/articles/s41598-024-78760-1))

### How to frame feedback so it doesn't demotivate a teenager

The sport-psych literature is direct on this: **informational feedback that emphasises progress and gives constructive guidance strengthens perceived competence and supports autonomous motivation, whereas feedback framed primarily in comparative or evaluative terms heightens anxiety and undermines need satisfaction.** Athletes with an improvement focus view setbacks as informational rather than controlling. ([Frontiers in Psychology — growth mindset and competitive motivation](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2025.1576649/full), [AASP — Revisiting Growth Mindset](https://appliedsportpsych.org/blog/2021/04/revisiting-growth-mindset-as-a-core-capacity-of-sport-psychology/))

This is a direct challenge to the existing `overall_rating: developing | on_track | performing | elite` label and to the red/amber/green attendance treatment — both are evaluative frames, and the four-tier label in particular reads as a ranking even though no other player is shown.

### Elite academy practice: the IDP is the vehicle, and coach feedback is what makes it work

Every EPPP academy player has a development plan built on the FA's Four Corner Model (technical, psychological, physical, social). Research using the TopTekkers app compared groups receiving weekly in-app IDPs **with and without coach feedback** — the coach-feedback layer is the differentiator. Older players (U14–U16) benefit from richer performance analytics that encourage self-improvement, whereas younger players need simple progress signals. Best practice is that IDPs are surfaced through multiple channels (video, athlete-monitoring software, shared documents) rather than living in one place. ([Premier League EPPP](https://www.premierleague.com/en/footballandcommunity/youth-development/EPPP), [The Coaching Manual — IDP research project](https://content.thecoachingmanual.com/blog/research-projectindividual-development-plans), [Hudl Lens — IDPs in football](https://www.hudl.com/blog/hudl-lens-individual-development-plans), [360Player](https://en-us.360player.com/product/player-development))

This validates the existing `/idp` and `/targets` pages but says the missing ingredient is the **coach reaction loop**, not more plan surfaces.

### Streaks work — and the failure modes are well documented

Duolingo's own metrics claim users with active streaks are 3× more likely to reach intermediate proficiency, with gamification lifting engagement ~60%. But the critique is equally well evidenced: streak mechanics can substitute extrinsic for intrinsic motivation ("users reported not logging in to learn any more"), and "streak creep" — piling on more and more streak-adjacent mechanics — reliably backfires. The mitigation that actually works is the **streak freeze**: an explicit safety net so one genuinely disrupted day doesn't destroy the accumulated investment. ([The Decision Lab — Streak Creep](https://thedecisionlab.com/insights/consumer-insights/streak-creep-the-perils-of-too-much-gamification), [StriveCloud — Duolingo gamification](https://www.strivecloud.io/blog/gamification-examples-boost-user-retention-duolingo), [Digia — Duolingo's habit-forming reminders](https://www.digia.tech/post/duolingo-habit-forming-reminders-retention-architecture/))

**Direct implication for this app:** a check-in streak is tempting because attendance data already exists — but attendance is a *compliance* behaviour with real-world consequences (safeguarding, college reporting). Streaking a compliance behaviour risks students gaming check-in, and risks a student who was genuinely ill feeling punished. If a streak is used at all, it should be on a discretionary behaviour (logging training, reflecting) and must ship with a freeze/excusal-aware rule from day one.

### Notification fatigue thresholds

**64% of users may stop using an app if they receive more than five push notifications per week**, and 46% will opt out at 2–5 messages in a week without clear relevance. The recommended architecture is: cap non-critical push at a few per user per day, **consolidate the rest into digests**, throttle to prevent storms, and segment caps by engagement level rather than applying one global cap. Opt-out rate per campaign is the signal to watch. ([Pushwoosh — 23 push notification best practices](https://www.pushwoosh.com/blog/push-notification-best-practices/), [Courier — How to Reduce Notification Fatigue](https://www.courier.com/blog/how-to-reduce-notification-fatigue-7-proven-product-strategies-for-saas), [indigitall](https://indigitall.com/en/blog/15-best-push-notification-strategies-to-boost-engagement-in-2025/))

Those thresholds are for promotional push; operational reminders have higher tolerance. But this app is already at 6–9/day for a Year-1 student with no way to turn any of it down.

### AI with under-18s: what the guidance actually requires

DfE's June 2025 guidance sets firm expectations on **data protection, safeguarding, age-appropriate use and human oversight** — "keep adults in charge of decisions" and "explain standards to families". ([DfE guidance summary — Browne Jacobson](https://www.brownejacobson.com/insights/latest-dfe-ai-guidance-for-schools), [Smoothwall summary for SLTs & DSLs](https://smoothwall.com/resources/dfe-guidance-on-generative-ai-a-summary-for-slts-dsls))

Internet Matters' *Me, Myself and AI* (July 2025) is the most directly relevant evidence for the AI Coach: **over a third of children who use AI chatbots feel like they're talking to a friend, rising to ~50% for vulnerable children; 12% of child users say they talk to a chatbot because they have no one else; 23% have used one to seek advice.** The named risks are inaccuracy, over-reliance, and privacy — and specifically that a chatbot can *replace* the trusted-adult contact that safeguarding depends on. ([Internet Matters — Me, Myself and AI (PDF)](https://www.internetmatters.org/wp-content/uploads/2025/07/Me-Myself-AI-Report.pdf), [HCR Law summary of updated DfE guidance](https://www.hcrlaw.com/news-and-insights/keeping-children-safe-in-the-age-of-ai-updated-dfe-guidance/))

**This is the sharpest external finding for this codebase.** The AI Coach at `app/api/ai/chat/route.ts` currently has no age-appropriate system-prompt guardrails, no disclosure that it is not a person, no distress-detection routing to a human, and no visibility for the DSL. Adding *more* AI touchpoints for students without addressing that first would increase risk.

## 4. Prioritised feature ideas

Effort key: **S** ≈ under a day, **M** ≈ 2–4 days, **L** ≈ a week or more.

---

### Tier 1 — highest impact, build first

**1. Weekly Recap ("Your week")**
A single Sunday-evening (or Friday-afternoon) screen and one consolidated push that summarises the student's own week: sessions attended, training logged, GPS distance vs their own previous week, any personal bests beaten, goals moved, coach ratings received, and one Claude-written sentence of encouragement grounded in their actual numbers.
*Need served:* competence + personal progress narrative — the single largest SDT gap. It is also the only thing on this list that makes the existing logging behaviours feel worth doing.
*Effort:* **M**
*Dependencies:* new cron route (**must be added to `vercel.json` in the same commit**); reuses `fetchPlayerData()` from `lib/ai/player-report.ts`; Claude (Haiku is sufficient — this is a short transform); a small `weekly_recaps` table for caching so the page is instant and the AI call happens once.
*Staff benefit:* replaces the nightly "your weekly focus is ready" push with something genuinely weekly, and gives staff a clean per-student weekly artefact to reference in 1-to-1s.

**2. Squad Feed with shout-outs**
A single scrollable feed on `/dashboard` or as a new tab: coach shout-outs, match results, "X hit a new top speed", "Y completed their IDP target", birthdays, fixture confirmations. Students and staff can react (one-tap emoji) and coaches can post a shout-out about a named student in two taps.
*Need served:* relatedness + recognition — the mechanic the evidence identifies as the strongest retention driver for this age group, and the one thing the app has zero of.
*Effort:* **L** (M if reactions are deferred to v2)
*Dependencies:* new `feed_items` + `feed_reactions` tables with RLS; existing chat/push infra for delivery; a staff composer in `app/(admin)/`.
*Staff benefit:* very high. Recognition from staff is *observable* in the data, and a student who stops receiving/reacting to feed items is a soft disengagement signal long before attendance drops. Also gives coaches a low-friction way to do the distributed-recognition practice the literature recommends.
*Safeguarding note:* staff-post-only for v1, with student reactions but no student free-text. Free-text posts by students would need moderation and should not be in scope initially.

**3. Activity Inbox + notification preferences**
Persist every push into a `notifications` table and render it as an in-app list (badge on the nav). Add a preferences screen on `/profile` with per-category toggles (check-in reminders, timetable, calendar, AI/coaching, social) and quiet hours.
*Need served:* autonomy (students choose what reaches them) plus basic reliability — right now a missed push is gone.
*Effort:* **M**
*Dependencies:* new `notifications` + `notification_preferences` tables; a shared send helper that writes the row *and* dispatches, replacing the ~15 direct `sendPushNotification` call sites.
*Staff benefit:* delivery becomes auditable — staff can see whether a student was actually told something, which matters for attendance and safeguarding follow-up. It also lets the 02:00 AI push be moved to a sane hour and demoted to inbox-only.
*Note:* safety-critical messages (safeguarding, urgent staff broadcasts) must be exempt from user muting.

**4. Personal-Best & progress framing pass**
Not a new page — a reframing of what already exists. Extend the "Personal Bests" pattern already in `components/gps/PlayerDashboard.tsx` across attendance, training, gym and match data. Replace "Attendance 78% ⚠ target 90%" with "78% — up 6 points on last month" alongside the target. Replace or supplement the `developing/on_track/performing/elite` label on the AI report with a movement indicator ("stronger than last month in X").
*Need served:* competence, framed informationally rather than evaluatively — directly addresses the growth-mindset evidence.
*Effort:* **S–M**
*Dependencies:* none new; all data already exists. Mostly presentation logic in `lib/` utils + the `PlayerReport` prompt in `lib/ai/player-report.ts`.
*Staff benefit:* indirect — students who feel the app is describing their growth rather than grading them are more likely to keep feeding it data, which improves the completeness of what staff see.

### Tier 2 — strong value, build after the loop is closed

**5. Make the AI report two-way and goal-linked**
Add three things to `/ai-report`: (a) a one-tap "Add this to my goals" on each `this_week_action`, writing straight into `student_goals`; (b) a "This doesn't feel right / I did do this" response the student can leave, visible to their coach; (c) show the student's own active goals and IDP targets *inside* the report so the four planning surfaces reference each other.
*Need served:* autonomy — the student becomes a participant in their plan rather than its subject. Matches the EPPP/TopTekkers finding that coach feedback is what makes an IDP work.
*Effort:* **M**
*Dependencies:* existing `student_goals`, `idp_plans`, `learner_reviews` tables; one new small `report_responses` table; no new AI.
*Staff benefit:* high and direct — a student saying "the AI thinks my nutrition is the problem but actually I can't get breakfast" is exactly the kind of context that never surfaces in a termly review.

**6. Post-match moment**
After a fixture the student was in the squad for, prompt once: rate your own performance, one thing that went well, one thing to work on. Show it back alongside the coach rating (already in `match_squads.coach_rating`) and the team result. Feed the reflection into the Weekly Recap and, with consent, into the coach's view.
*Need served:* immediate feedback tied to the moment that matters most to a young footballer; reflection is also a BTEC-assessable behaviour.
*Effort:* **M**
*Dependencies:* extends existing `match_logs` / `match_squads`; one triggered push (not a new recurring cron).
*Staff benefit:* gives coaches a self-assessment to compare against their own rating — a large gap between the two is a useful conversation starter and, when persistent, a wellbeing signal.

**7. Wellbeing check-in that gives something back**
After submitting the fortnightly survey, show the student their own 6-month trend (`components/wellbeing/WellbeingSparkline.tsx` already exists — it's just staff-side), one relevant Learning Hub resource matched to their lowest-scoring dimension, and an explicit "a member of staff will see this" transparency line. Optionally offer an ultra-light daily one-tap mood check as a separate, opt-in thing.
*Need served:* reciprocity — closing the most extractive loop in the app. Also improves honesty: students answer more truthfully when they can see what happens to the answer.
*Effort:* **S** for the trend + resource + transparency line; **M** if a daily check-in is added.
*Dependencies:* none new for the S version.
*Staff benefit:* directly improves the honesty and completeness of the wellbeing data the pastoral team relies on. **Caveat:** the daily-check-in variant overlaps with the separate wellbeing-dashboard research effort — coordinate before building.

*Effort:* **S** to remove; **M** to make `/veo` a manual clip surface.

**9. Navigation consolidation**
Add `/performance` to the nav (currently unreachable except via a link on the Catapult page). Align the mobile "More" sheet and the desktop `SideNav` so the same features exist in both. Consider making the dashboard tool grid the canonical "everything" surface and trimming the nav.

*Effort:* **M**

## 5. Notification-budget note

**Yes — the cumulative list would over-notify, and the app is already at the limit before any of it is built.**

A Year-1 student on a normal Tuesday, with everything working, receives roughly:

| Time | Source | Count |
|---|---|---|
| 02:00 | `refresh-reports` "your weekly focus is ready" | 0–1 (fires whenever a `high` dev area exists — i.e. most nights) |
| 08:00 | `check-in-nudges` morning | 1 |
| 09:00 | `calendar-reminders` — one push **per event** tomorrow | 0–n |
| through the day | `timetable-reminders` — 15 min before each slot | 3–5 |
| 11:45/12:45 | `lunch-ending` | 1 |
| 12:00 | `check-in-nudges` lunch | 1 |
| 15:00 | `check-in-nudges` end of day | 1 |
| any time | chat messages, nudges, squad invitations | variable |
| **Total** | | **~6–9 per weekday** |

Against a benchmark where >5 per *week* causes ~64% of users to disengage from promotional push, and with **no mute, no quiet hours, no per-category control and no in-app inbox to fall back on**, adding a recap push, a feed push, a match-reflection push and a challenge push would take this to 10+ and the rational student response is to turn push off entirely — at which point the safeguarding-relevant messages stop arriving too.

**Recommended sequencing — consolidate before adding:**

1. **Build the Activity Inbox + preferences (idea 3) first.** Nothing else on this list should ship until there is a place for a message to land that isn't a push. This is a prerequisite, not a feature.
2. **Fix the mislabelled nightly push.** `refresh-reports` runs at 02:00 daily and sends a message titled "weekly". Either gate it to once per week, or demote it to inbox-only and let the Weekly Recap carry it.
3. **Cap `calendar-reminders`.** It currently loops over every event and sends one push each. Roll multiple next-day events into a single "3 things on tomorrow" push.
4. **Consider merging the three `check-in-nudges` into two**, or suppressing the nudge entirely for students who have already checked in (worth verifying whether it already does this).
5. **Budget the new features to one push each, max:** Weekly Recap = 1/week. Squad Feed = **inbox-only by default**, push only for shout-outs that name the student personally. Post-match reflection = 1 per fixture, triggered not scheduled. Challenges = inbox-only.
6. **Net target: ≤4 pushes on a normal weekday, ≤6 on a match day.** That means the new features should be roughly cost-neutral, funded by the consolidations in steps 2–4.
7. **Instrument opt-out rate.** Track `push_subscriptions` deletions and native-token churn per week so over-notification is visible rather than inferred.

## 6. Open questions for Paul

1. **Social layer — how far, and who moderates?** Squad Feed with staff-only posts and student reactions is low-risk. Student free-text posts are a different product with a moderation burden and a safeguarding surface. Which are we building? And who is accountable for reading it daily?

2. **Comparison — is any peer-visible number acceptable?** The research is clear that comparative framing harms the students at the bottom, who are usually the ones we most need to keep engaged. Are collective/team numbers the ceiling, or is there an appetite for opt-in per-player comparison? This decision determines whether ideas 10 and 11 are in scope at all.

3. **Is a streak wanted at all?** It's the most requested-sounding mechanic and the one with the weakest evidence for this specific context. My recommendation is no streak in v1. Confirm.

4. **AI Coach guardrails — when?** This is the one item on this list that is a risk, not an opportunity. Right now `app/api/ai/chat/route.ts` is a general-purpose Sonnet with a one-line system prompt, available to minors, with no distress routing, no "I am not a person" disclosure, and no DSL visibility. Internet Matters found ~a third of child chatbot users feel they're talking to a friend, and 12% use one because they have no one else. Before any new AI features ship for students, we need a decision on: an age-appropriate system prompt, a safeguarding escalation path (a distress signal opens a `safeguarding_concerns` row or nudges the DSL), a visible transparency line, and whether chat transcripts are retained/reviewable. **Does this become a blocking prerequisite for Tier 1, or does it run in parallel?**

5. **Notification authority — who owns the budget?** If we're capping at ~4/day, someone has to be able to say no to the next reminder request. Is that a product decision Paul owns, or does it need academy/college sign-off?

6. **VEO and Catapult — remove or replace?** Both tiles are dead ends and have been since at least the 2026-06-10 feature review. Are the API credentials realistically coming this term? If not, pulling them from the dashboard grid is a 30-minute job that measurably improves the app.

7. **Wellbeing overlap.** Idea 7 (giving students their own wellbeing trend back, plus an optional daily check-in) touches the same data as the separate coach/admin wellbeing-dashboard research. Should these be planned as one piece of work, and does the pastoral team have a view on whether students should see their own historic scores?

8. **Parents.** There is a full parent portal (`app/(parent)/`). Does anything student-facing built here — recap, shout-outs, match reflections — mirror to parents? That is a meaningful engagement multiplier and also a meaningful consent question for 16–18 year olds.

9. **What does success look like?** Before building: is the target daily-active students, wellbeing-survey completion rate, training-log volume, or something staff-facing like "fewer unexplained absences"? The Weekly Recap and the Squad Feed optimise for different ones.
